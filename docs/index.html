Browser-to-browser data channels with CRDT state sync that

need no server at all mesh a whole room in seconds keep your data off the server merge offline edits without conflicts heal dropped links on their own

defuss-webrtc wraps WebRTC so that two peers only have to exchange one offer and one answer. Both travel as self-contained JSON: by hand as a file, or through a tiny room signaling server that ships in this repository for Node.js and for Vercel. Once the data channel is open, a schema-aware CRDT keeps one JSON document in sync between every peer.

One offer, one answer

ManualPeer waits until ICE gathering is complete, then returns a SignalBundle: complete SDP with every candidate, no trickle ICE. Signaling is exactly two JSON messages.

Signaling without a server

A bundle is a file like any other: send it by chat, email, QR code or USB stick. The peers only need a way to pass two files, and nothing else stands between them.

Rooms in seconds

The room server pairs every newcomer with every member: the joiner offers, the members answer, and polling doubles as the presence heartbeat. Node.js or Vercel, one protocol.

Your data stays between peers

After signaling, application traffic flows peer to peer. A signaling server holds members, offers and answers, never a message; offers and answers expire after 120 seconds.

Conflict-free by schema

The schema names the merge rule of every path: last-writer-wins register, counter, add-wins set, map, RGA list. Replicas converge in any delivery order, also after days offline.

Zero dependencies

ES modules with TypeScript declarations, built on the browser's own RTCPeerConnection. No runtime dependencies; STUN defaults to Cloudflare's public server, TURN plugs in through iceServers.

How it works

💡 Signal once, then sync directly

WebRTC can only open a data channel after both peers know each other's session description: codecs, ICE credentials, DTLS fingerprints and the network addresses (candidates) where they might be reachable. Getting that across is signaling, and WebRTC leaves it to you. defuss-webrtc packs it into one offer bundle and one answer bundle, so any channel that can carry two JSON messages will do. Press play on each diagram, or click a box or an arrow to read what it does.

A

Automatic: a room on the signaling server

The room server is a rendezvous point, not a relay. Peer B joins a room in which Peer A already waits, offers to every member it finds, and both sides poll until the offer is answered. ICE then finds a network path between the browsers, and the server drops out of the picture.

B

Manual: two files, no server

The same two bundles can travel by hand. Peer A downloads its offer as PEER.json and sends it any way it likes; Peer B uploads it and gets an answer file to send back. The offering tab must stay open until the answer arrives, because the offer belongs to a live RTCPeerConnection: a bundle is short-lived session state, not a contact card.

Click a box or an arrow to read what it does.
C

CRDT over the open data channel

doc.attach(channel) binds one CRDT document to a reliable, ordered data channel. On open, both sides send hello with their canonical schema and version vector; each then sends the operations the other lacks. Every local write becomes one operation (actor, seq, Lamport clock) that goes to every attached channel, and a peer forwards what it learns to its other channels, so a mesh needs no central copy.

What heals by itself

  • lost link

    Network drop, sleep, ICE failure: the data channel and connectionState notice, and the later joiner of the pair offers again, with backoff.

  • offline

    Signaling pauses, writing goes on. The online event resyncs at once, and the CRDT merges what both sides wrote while apart.

  • hidden tab

    Polls every 15 seconds instead of every 2, well inside the server's 90-second presence timeout, and resyncs the moment it is visible.

  • dropped

    A tab the server timed out (asleep for more than 90 seconds) notices that it is missing from members[] and rejoins on its own.

The demo's reconnection logic, tested in real Chromium peers by e2e/browser/chat.spec.mjs.

Signaling server

🛰️ Host the room server yourself

The repository ships two interchangeable implementations of one protocol, server/PROTOCOL.md, and one conformance suite (e2e/signaling.test.mjs) that runs against any deployment. Both return identical responses; they differ in where a room lives and how it expires. The demo above uses the hosted Vercel deployment.

Where rooms live
In the memory of one Node.js process: a RoomStore holds a Map of rooms, and each room holds Maps of members (by peerId), offers and answers (by sessionId). A restart empties it.
Atomic writes
Every request runs synchronously against those maps on one event loop, so a join or an answer is never half done.
Expiry
A timer sweeps every 30 seconds: members silent for 90 seconds leave (with the full cascade below), offers and answers older than 120 seconds go.
Scaling
One process. Two instances would each know only their own rooms, which is why the serverless port moved the state out of the process.
Configuration
PORT (default 8787) and an optional SERVER_PASSWORD. JSON bodies up to 256 kB, CORS open to every origin.
Where rooms live
In Upstash Redis, through its REST API. Each room is one JSON document { revision, room } under {defuss-webrtc}:room:<name>; the sorted set {defuss-webrtc}:rooms lists the rooms by createdAt.
Atomic writes
Each mutation is computed in TypeScript and committed by a Lua compare-and-swap on the revision, room and index in one script. A writer that lost the race retries from the newest revision, up to 24 times. Reads run as Lua on the primary, so a lagging replica cannot hide a fresh room.
Expiry
Lazy: every room access and every room listing sweeps first (members after 90 seconds, offers and answers after 120). Room keys also expire 180 seconds after their last write, as a safety net for dead rooms.
Scaling
Stateless function instances share one Redis. vercel.json pins the function to fra1; keep it next to the Redis primary.
Configuration
UPSTASH_REDIS_REST_URL + UPSTASH_REDIS_REST_TOKEN (or KV_REST_API_URL + KV_REST_API_TOKEN from the Vercel Marketplace), and an optional SERVER_PASSWORD.

🗂️ What a room holds

A room is a named rendezvous point: who is in it, and the offers and answers in flight between them. It is a channel for signaling only. Messages never pass through it: every pair of members gets its own RTCDataChannel, and the demo's CRDT document, named after the room, syncs over those channels. Both servers store exactly this model; GET /v1/rooms shows only name, member count, createdAt and whether the room is protected.

Moderation

The creator is the moderator, and every room has exactly one. When the moderator leaves or times out, the remaining member with the smallest joinedAt takes over. The role grants no extra endpoint: it marks the longest-standing member, and the demo shows it as ★.

Full mesh

The joiner offers to every member, so N members hold N·(N−1)/2 connections. When two peers join at the same moment and miss each other, the one with the later joinedAt sends a late offer.

Presence

There is no push: peers poll GET …/members?peerId=…, and each poll is the heartbeat. A peer that finds itself missing from members[] was timed out and must leave locally; the demo rejoins.

Passwords

Optional and independent: a server password in X-Server-Password, a room password in X-Room-Password. They gate who may use a server or room, but there is no per-member login and peerId is self-asserted: terminate TLS and rate-limit public deployments.

CRDT explorer

🧪 Edit two replicas offline, then merge them

Two replicas of one CRDT document start from the same state, lose their connection, and change it independently. Merge hands each replica what it lacks, exactly what attach() sends after the hello, and both end up identical. The calls run in your browser, on the defuss-webrtc build this page ships.

API

📚 Two entry points, plain JSON on every wire

defuss-webrtc/webrtc connects peers, defuss-webrtc/crdt syncs state; the package root exports both. Bundles, snapshots and wire messages are plain JSON. The declarations ship in dist/; the source of truth is src/.

One ManualPeer is one RTCPeerConnection with one ordered data channel, for one pairing. Its bundles wait for complete ICE gathering, so no trickle ICE is needed.

Base path /v1, JSON in and out, CORS open. Errors are { "error": "CODE", "message": "…" }; clients branch on error. Room names match ^[a-zA-Z0-9_-]{1,64}$.

createCrdtDocument({ id, schema, actorId?, maxMessageBytes = 65536, maxBufferedAmount = 524288 }) returns a document. The schema decides the merge rule per path:

Schema nodeMutationsMerge semantics
register(initial)set(path, value)Lamport last-writer-wins; (clock, actor, seq) breaks ties.
counter(initial)increment(path, delta = 1)Unique, immutable deltas, each summed once.
orSet(initial)setAdd, setDeleteObserved-remove: an add wins over a concurrent delete.
map(valueSchema)nested writes, mapEnsure, mapDeleteLast-writer-wins key lifecycle; a re-put starts a fresh nested generation.
object(fields)child writesA static container of fields.
list(initial)listInsert, listSet, listDeleteRGA-style: immutable element ids plus tombstones.
Document memberSemantics
state, get(path)The materialized JSON, as a fresh copy; one path of it.
subscribe(listener)Called with { origin: 'local' | 'remote' | 'import', ops, state }; returns an unsubscribe function. onError(listener) reports wire and schema errors.
batch(fn)Several writes, one broadcast and one notification.
attach(channel)Syncs over a reliable, ordered RTCDataChannel (any number of them); returns detach. close() detaches all.
export(), merge(snapshot)The operation set as a JSON snapshot; merging returns how many operations were new.
versionVector, operationCountThe highest contiguous seq per actor; the number of operations held.

Every message on a data channel is a UTF-8 JSON string with protocol: "defuss-crdt/1" and the docId; messages for another document or protocol reject the channel.

kindFieldsWhen
helloactorId, schema (canonical), schemaFingerprint, vector, replyOn open by both sides; a non-reply hello gets a reply hello, and either one triggers the missing operations.
opsops: CrdtOp[], each with id, actor, seq, clock, kind, pathCatch-up, every local write, and gossip of newly learned operations; chunked under maxMessageBytes.
errorcode, messageBefore a side rejects the channel, e.g. SCHEMA_MISMATCH; the other side reports REMOTE_<code>.

A snapshot from export() is { protocol: "defuss-crdt/snapshot/1", docId, schema, schemaFingerprint, ops }. It holds every operation, so it grows with the writes; compaction is not implemented in 0.1.

Install

🧑‍💻 Add it to your app

Install it from npm, or import it straight from a CDN. Then pick a signaling mode, attach a CRDT document, or hand one prompt to your coding agent.

From npm

ES modules with TypeScript declarations: defuss-webrtc, defuss-webrtc/webrtc and defuss-webrtc/crdt. No runtime dependencies.

In the browser, no bundler

The published dist/ is plain ES modules, so an import map pointing at jsDelivr is enough.

Use it

Connect by hand or through a room, then attach one CRDT document to every open channel. The demo's app.js is the complete room client, with leaving, errors and mesh repair.

Vibe coding

Paste this prompt into your coding agent. It links the repository, so the agent works from the current README and protocol.

Read its README.md and server/PROTOCOL.md first. Connect peers with ManualPeer bundles (complete SDP, no trickle ICE), through the room server or by hand as JSON files.
